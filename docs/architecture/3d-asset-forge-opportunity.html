01 / THESIS

引擎控制不是瓶颈，资产可用性才是。

Unity 和 Unreal 的 CLI/MCP 已经能让 Agent 创建场景、导入资源和运行验证。真正缺少的是生成器与引擎之间那层可靠的资产编译管线。

Core product thesis

不再做一个通用引擎 MCP，也不从零训练 3D 模型。构建一个中立的 3D 资产检查、修复、优化与交付层。

02 / SHIFT

从“生成并调用”转向“编译并验证”。

SpriteCook 的启发是完整工作流，而不是某一个模型。3D 需要在同样的 Agent 闭环中，增加一层更严格的质量门槛。

2D / proven loop

SpriteCook × Codex × Godot

稳定的精灵生成能力加上 Codex 开发能力，再由 Godot 完成场景利用与验证。资产复杂度低，闭环短。

生成精灵→稳定资产 ID→组装场景→运行
3D / proposed loop

Provider × Compiler × Engine

3D 不能把生成结果直接交给引擎。模型必须先通过规范化、检查、确定性修复和引擎适配。

生成 / 导入→检查→编译→引擎验证

03 / FIELD

生态足够成熟，产品层仍有空位。

现有工具已经覆盖编辑器控制、DCC 操作与 Web 预览。应当组合它们，而不是重复建设它们。

Unity

First adapter

Batchmode、AssetDatabase 和 ModelImporter 形成稳定自动化基础；Unity MCP 生态最成熟，也最适合证明“模型到可运行 Prefab”的闭环。

第一个目标引擎，但不是产品本身

Unreal

Second phase

Interchange Framework 很强，但版本、插件、材质和编辑器自动化复杂度更高。先做预检与可重放导入，再扩展深度控制。

高价值的第二阶段适配器

Blender

Compiler backend

后台模式与 Python 适合格式转换、UV、烘焙、拓扑、绑定和碰撞。它解决浏览器无法可靠处理的重任务。

内部无头编译器，不做主界面

Web3D

Inspector UI

Three.js、model-viewer、glTF Validator、glTF-Transform 与 meshoptimizer 组成快速、开放、跨平台的检查层。

预览、诊断、配置与任务编排
04 / PRODUCT

卖的不是“另一个生成器”，是可交付结果。

服务那些能获得 3D 模型、却无法判断模型是否可用或不愿承担 Blender 清理成本的开发者。

Core job to be done

“给我一个来源不确定的模型，告诉我哪里有问题，安全修复能修的部分，并交付到目标引擎。”

  • AI 3D 用户与独立开发者
  • Unity / Unreal 小团队
  • 跨 Web 与引擎交付的创作者
  • 使用 Codex 构建 3D 原型的开发者

06 / MVP

先回答“能不能用”，再回答“能生成什么”。

首版不包含生成。聚焦一个 GLB 从进入工作台，到输出报告、优化文件和 Unity 导入结果的完整闭环。

  1. 拖入单个 GLB，建立资产 ID 与来源记录
  2. Web3D 预览模型、材质和动画片段
  3. 报告三角面、材质、贴图、骨骼和 Bounds
  4. 识别规范、单位、朝向与 PBR 完整性问题
  5. 执行归一化、贴图压缩和网格优化
  6. 导出优化 GLB、JSON 报告与本地 Job 清单
  7. 生成 Unity Import Profile 与 Prefab
  8. 在固定测试工程中完成无人工冒烟验证

关键风险

  • R01
    免费单点工具已经成熟必须用完整工作流、时间节省和引擎交付形成价值。
  • R02
    能力可能被生成平台吸收保持 Provider-neutral，专注跨来源、跨引擎一致性。
  • R03
    Web 无法替代专业 DCC浏览器做检查，Blender Worker 处理重任务。
  • R04
    自动优化可能损害结果提供前后对比、可逆 Job、阈值和 Fixture 回归。
  • R05
    付费意愿尚未直接验证先卖人工辅助清理服务，再搭建完整产品。
